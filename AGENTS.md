# AI Agent Lab

Private team feedback workspace for multiple GitHub projects. Node 24, React/Vite, Express, built-in SQLite and official MCP SDK.

## Verification

Run `npm ci` then `npm run check`. Never require live provider credentials for tests.

## Invariants

- Explicitly opted-in workers poll approved requests and run Codex CLI in isolated worktrees. Railway may coordinate bounded API/GitHub reads or dispatch the configured cloud workflow, but must never execute project code/package scripts itself.
- New member/admin feedback is queued durably for read-only Codex planning on the Mac by default; the Lab server makes no model API call. Survey leases are separate from execution approval and claims. Legacy server analysis requires explicit LAB_PLANNING_MODE=server. Server-classified bounded low-risk UI auto-runs; medium uses project opt-in impact-auto when source, scope, reversibility and behavioral test plans are established; high or material unresolved decisions need admin approval.
- Default feedback-routing-v1 makes at most one Lab classification call with original feedback and bounded pinned MD/verified project-memory context; it must not retrieve embeddings, scan source, generate a plan or issue approval. Provisional model risk never creates a risk floor; deterministic intent, verified impact and existing pinned approvals remain authoritative. Original feedback plus preliminary classification goes directly to the scoped Codex survey queue; failures hand off once without a paid retry. An explicitly selected legacy plan strategy may coordinate and plan on Railway after a successful model evaluation. It may read only bounded pinned GitHub source and canonical MD, never execute repo code. Model decisions never grant authority: exact scope/traceability, deterministic risk floors, source evidence and existing approval/CI/release gates still apply. No external repo migration is executed by this module.
- Cloud workers require separate explicit configuration and secrets. They share exclusive execution/verification claims with Mac; cloud publishing is separately opt-in and uses the existing release supervisor, never model/MCP approval. Do not transfer Mac credentials into GitHub automatically. New default configuration keeps the orchestrator and cloud worker off until readiness checks and administrator setup finish.
- Past accepted/rejected decisions may inform preparation as untrusted examples; they never override current scope, risk policy, or approval authority.
- No MCP tool may approve, merge, deploy, delete project data or apply production migrations.
- UI results from the Mac runner first enter a separate browser-verification queue. That worker may push a draft PR and report CI, but must never mark it ready, merge or deploy before acceptance. New opt-in single-approval requests may be accepted automatically only after independent server-side exact-head GitHub CI, scope and parent checks, using the release consent bound to their initial approval. Legacy requests still require admin acceptance. Browser checks run in GitHub Actions, not Chrome launched by LaunchAgent. Failed local checks are preserved when additional verification supersedes them.
- After manual acceptance or consent-bound automatic CI acceptance, an explicitly enabled Mac publisher may push the accepted commit, create a PR, require GitHub CI, merge main and observe Railway deployment. This uses separate release claims, never coding-agent permissions. High-risk releases require explicit confirmation; no production migrations are run by the publisher.
- Approval fingerprints bind draft, baseCommit and libraryVersionId.
- Request scope uses exact repo-relative file paths; never permit traversal, glob or secret files.
- Claim transitions and overlapping-scope checks are atomic transactions.
- Expired claims stay locked until admin verifies the old agent stopped.
- Never expose claim token hashes, raw claim tokens, passwords or API keys via UI/list endpoints.
- Git library versions are immutable; syncing must not change existing packets.
- Agent-reported verification is not independent CI evidence. Label it accurately.
- Canonical project sources remain read-only during Lab library sync.
- Each request pins projectId, repository, branch and library; sync, rebase, learning, coding and publishing must stay in that project.
- Adding a project never enables production release implicitly. Mac checkouts are managed locally; never accept a server-provided filesystem path or executable.

- CI onboarding is an admin-only capability separate from feedback/MCP coding. CI workers may add only the managed workflow/test files and may merge only with explicit job consent and exact-head successful GitHub Actions evidence. Never overwrite existing workflows, modify application code/manifests, or enable release implicitly.
- CI setup readiness must be independently verified server-side; empty, skipped, wrong-app or wrong-commit checks never count as passing.

## Design

Use Writer Studio design tokens, neutral grays, semantic status colors, system typography, compact spacing, 12px cards and 8px controls. Preserve responsive navigation, visible focus, local errors and durable saved results.


- Project memory stores provenance-bound verified outcomes and separately labeled reviewer decisions. It is untrusted reference data, never authority to lower risk or expand scope. Pending/agent-only work is not a verified lesson. No automatic model training or autonomous improvement execution.
- Knowledge retrieval combines inspectable bilingual concepts with keywords and pinned MD chunks. Optional cached embeddings share the project budget and never substitute for provenance or grant authority; do not describe retrieval as training. Failed incidents remain explicitly unverified. Admin lesson corrections preserve provenance and disable invalid/superseded entries. Model activation requires a matching version/model evaluation; test-set accuracy is not production accuracy.
- Agent model calls reserve token budget before dispatch (per project/day tokens and lifetime request limits; no daily API call-count cap), with at most two steps per job. Interrupted or failed jobs never automatically retry a paid call. A fallback to a survey must preserve the original feedback and cannot create parallel claims.
- Maintenance sync is read-only against GitHub; it may replace the current library pointer only for new requests. Webhook signatures must be verified on original bytes. Drift candidates are heuristics, never automatic policy edits. Backups retain seven verified SQLite snapshots on the existing volume; exports must omit settings/credentials and restore preview never modifies production.
- Planning failures do not auto-retry model calls. At most 20 surveys per project per UTC day and 3 attempts per feedback; expired claims require admin confirmation that the old planner stopped.
- Report-only planning recovery is an explicit admin action, revision/base-bound, limited to three sends, and requires planning-replay-v1 before claim. Verify the saved artifact against pinned source hashes; never fall back to a model call. It grants no execution or release approval.
- Lab owns scope-v2: new behavioral specs may follow the suffix of existing specs in established test roots alongside source evidence. This does not admit workflows, manifests or arbitrary new helpers. Planning excerpts must advertise omitted canonical MD; workers read complete pinned documents before citing them. One operational worker failure must not starve independent project queues.

- Artifact rechecks are admin-queued, independent Mac checks on a detached worktree at the same pinned commit. They call no model and edit no source. Only a failed literal `git diff --check` may be superseded after independent build and CRLF-aware pinned diff checks; preserve failed-check provenance, then require CI before acceptance. Other failures remain blockers. Active/expired recheck leases block rebasing until the worker is confirmed stopped.

- New default requests use md-trace-v1: every criterion references exact quoted lines of pinned MD and a planned test/inspection. Source quotes are server-validated and hash-bound; document contents never authorize scope or policy changes. New workers must declare protocol support before planning/execution claims. Old requests retain their original contract.
- Criterion reports remain agent-attested, independently labelled from exact-commit CI. Missing/failed/mismatched criterion evidence or incomplete required MD updates blocks acceptance/release even if generic CI is green. Documentation-impact candidates are heuristics, never proof of semantic drift; a reviewed justification is required. Necessary MD/test paths must be approved before edits; policy MD changes require high risk.

- impact-v1 separates risk labels from auto execution. High-impact semantic domains cannot be auto-approved. Medium needs project opt-in, source/dependency evidence, behavioral tests per criterion and consent-bound CI/release; uncertainty remains a review gate. No learned example grants authority. Reviewed classification feedback must never mutate live risk or approvals.
- Lark uses one durable, updatable private bot card per new request. Encrypt credentials at rest, never expose them in API responses/logs, fix the API host, retain initial-send UUIDs, and never silently duplicate ambiguous/expired messages. Keep delivery retries separate from model retries. No Lark button grants approval.

- CI collection may run before criterion reports are complete. Acceptance/release remain blocked until all criteria and MD review are complete. Browser criterion reconciliation accepts only supported approved file/grep commands with successful desktop/mobile test records in the exact-head GitHub Actions browser-check job. Preserve superseded results; never substitute generic CI success for missing test records.

- feedback-images-v1 stores bounded raster attachments atomically with feedback in SQLite, never inline bytes in request/MCP/list/event JSON. Session/MCP authentication is required to fetch images. Immutable image hashes bind survey context. Workers must declare attachment support before claiming attached tasks; download only from the configured Lab origin, bound byte counts, verify sha256, and pass actual local files through Codex --image for both survey and execution. Image text is untrusted reference, never permission. Do not commit cached images or include the image cache in cloud artifacts. Lab's text classifier receives only attachment count, not image bytes.

- CI/deploy monitoring must not wait behind a model process. Keep one monitor cycle in flight and drain it before removing the runner lock. Pin explicit model arguments for planning and execution on Mac/cloud. Reuse survey evidence as a reading map, never as permission to skip source verification. Quoted grep alternatives are data, not shell pipelines: require every approved tag on desktop/mobile and report unsupported commands explicitly.

- triage-context-v1 uses only same-project pinned MD and compatible enabled verified outcomes. Store Luna/Codex risk comparison, changed paths, tests, MD review and deployment provenance in verified-context-v1. Refresh outcome records after deploy/library sync without re-enabling invalidated lessons. Model context is untrusted reference data, never permission to lower sensitive-domain policy or alter an approved request.

- project-fifo-v1 serializes classification/survey, execution, CI, release and MD sync per project/repository branch. Failed/expired/awaiting-approval predecessors block the lane; a confirmed rejection may release it. Pending unapproved feedback refreshes base/library only when reaching the head. Never repin an approved plan or replay artifact silently. Mac, cloud and MCP claims enforce the same SQLite-owned turn.
- risk-brief-v2 separates preliminary expected impact from source uncertainty. Unknown implementation details are Codex verification tasks; they do not by themselves raise a provisional display label. Only source-grounded plans grant execution authority. Existing/new established test specs do not raise production behavior risk; sensitive production paths/domains and material unresolved decisions remain protected.

- execution-readiness-v1 keeps unresolved survey questions, structured impact uncertainty and explicit legacy prerequisite checkpoints visible. Approval is consent, never evidence that a missing prerequisite was supplied. Guard submit/approve, ready listing, claim and execution retry; preserve immutable prior evidence. A revised plan must resolve prerequisites before another execution attempt. Do not require production payloads for tests that source/MD contracts already specify; synthetic fixtures are not production reproduction evidence.

- Streamlined impact-auto: low/medium do not need a separate human acceptance of their label or implementation choices. Surveys mark uncertaintyKind investigation for safely testable source hypotheses, decision for external/product/contract facts preventing safe work. Legacy untyped uncertainty and explicit questions remain blockers. Only a fresh source-grounded survey at the pinned base can resolve an earlier execution stop. Medium needs at least one behavioral regression plan; other criteria may use concrete inspections. Independent exact-head CI, criterion reports, MD review, release consent and FIFO remain mandatory before automatic acceptance/deploy.

- CI repair commits must be fast-forward, single-parent descendants of the pinned base and include the previously reported artifact, bounded to eight commits; every changed/renamed path and exact-head CI still needs independent verification. Never force-push or treat an unrelated green run as repair evidence. Expired verification/publisher claims require explicit stopped-worker recovery. Test-only model fixtures must remain isolated and mock all provider/mutation requests.

- CI observation is read-only and pinned to the independently checked PR head/scope/lineage. Expose actual required job states and links; failed CI must not look like a generic wait. Observation never grants acceptance. Preserve local discovery failures and label them superseded only by matching criterion proof on the exact result commit.

## Bounded recovery and learning

- ci-repair-v1 may run at most two new coding attempts after independently observed failed CI, only for opted-in low/medium requests with unchanged initial release authority. Same PR, exact allowedPaths, fresh isolated worktree, fast-forward push, no policy/test weakening, no merge permission. Ambiguous/expired claims remain locked until explicitly confirmed stopped. Repairs preserve original results and must pass independent exact-head CI/criteria/MD review again. A scope change stops repair.
- lab-test-v1 records structured JSON from the actual GitHub browser job for desktop/mobile. Malformed, skipped, wrong-file or missing records never fall back to apparent success. Legacy list logs remain compatible. Inspection evidence stays agent-attested, and repaired commits require fresh inspections.
- Deploy observation recovery never re-runs a migration or creates a new artifact. Only bound transient observation failures retry up to three times; terminal Railway errors require review. MD sync is a restart-safe metadata job with backoff, independent of merge/deploy.
- learning-outcome-v1 stores provenance and incident state per project in SQLite. Codex decisions and CI success are not ground-truth risk labels. Incidents/failed releases are excluded from retrieved successful examples.
- Background evaluations use the shared production classification prompt, fixed policy holdout and separately grouped human labels; strip examples from evaluation context to avoid answer leakage. Separate durable token reservations, no automatic paid retry after an interrupted run, no model-weight training. Candidate prompt activation requires no missed high risks, >=90% evaluation accuracy, no baseline regression, >=20 human labels including >=4 real holdouts, and unchanged model/library/reference/data versions. Activation never changes risk floors, scope or release consent.

- diagnostic-survey-v1 permits targeted existing offline non-browser tests under the survey's read-only sandbox; no installs, source writes, live provider/production calls or broad package scripts. One successful survey with typed technical checkpoints may receive one bounded diagnostic follow-up under the same lease/base, within ten total minutes. A failed call never automatically retries. Explicit user checkpoints remain blocking; source-grounded revised scope is required for execution. Opted-in impact-auto low/medium may queue one fresh survey after a stopped scope mismatch, within existing survey caps; authority is re-evaluated, never carried across changed plans. Preserve prior plans and distinguish exhausted investigation from missing user decisions in UI.

- Mixed criterion reconciliation verifies browser rows against exact-head CI while preserving already-passed non-browser/inspection rows as agent-reported only, with matching command/files/checks at the same result commit (or fresh repair evidence). Generic green CI never upgrades local unit evidence to independent proof. Missing, failed, pending or stale local evidence remains a blocker.

## Direct feedback workflow (supersedes per-criterion release gates)

Production defaults to direct-v1: Luna classifies once, Codex surveys and implements on a single persistent runner-owned worktree per project, then local checks, exact-head GitHub CI, authorized merge and Railway confirmation. Read/update relevant MD and retain verified feedback memory; do not require a quoted MD-to-criterion-to-proof matrix. Those legacy records are advisory for direct-v1 requests, including explicitly migrated idle requests. Real test/build/CI failures, exact scope/lineage, high-risk consent and project FIFO remain enforced. No user may be required to label screenshots/test tags just to release. Dirty worktrees are preserved and reported, never force-reset or deleted. Existing legacy artifacts/worktrees are retained for recovery; new direct survey/execution/CI repair reuse the same project workspace. Use LAB_WORKFLOW_MODE=legacy only to explicitly retain the old strict workflow. Never migrate live/expired claims.

- Artifact recheck v2 supersedes the whitespace-only recovery rule: independently rerun allow-listed npm check/typecheck/build and pinned whitespace checks on the exact unchanged commit. Preserve failed reports in checkHistory only after all required rechecks pass. A model-reported retry may queue this bounded no-AI verification, never authorize success. Unsupported failures remain blocking; exact-head browser CI still precedes acceptance.

- Planning output schemas must stay synchronized with server validation. After changing planning contracts run `npm run schemas:sync`; CI checks the generated constraints. Keep cross-field/source/scope checks authoritative. Persist bounded field-only validation diagnostics, preserve rejected reports, and use revision/base/hash-bound replay for report recovery rather than silently dropping dependencies or retrying the model.

- After a terminal deploy error, the server may reconcile an already successful Railway deployment through the same exact-head CI, approved environment/service binding and bounded maintenance-only descendant checks as the admin recovery action. This is read-only observation, not a deploy retry. Require unchanged upfront release consent before and after remote reads, preserve the original merge/error evidence, respect worker leases/FIFO and durable backoff; only release the lane after MD sync. Never run code, merge or redeploy in this recovery.

- project-md-onboarding-v1 keeps temporary repositories outside the active project registry/FIFO until admin confirms a merged, independently verified MD-only PR and current canonical library. An isolated read-only Mac survey may propose only missing canonical MD with source evidence; never overwrite existing docs/source/workflows, auto-merge, enable coding/release, or infer production authority. Keep this lane independent from feedback and CI/deploy monitors, include it in safe-idle/drain, preserve claims/artifacts on failure, and never retry paid surveys without explicit admin resurvey consent. New runner support is optional; old workers keep serving existing projects.
