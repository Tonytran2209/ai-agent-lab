# Railway link and operational activation

Admin Settings → Project & tự động → a project → **Liên kết deploy & hoàn tất**. This third phase links an existing Railway service; it never provisions services, writes Railway settings/variables, deploys code or runs migrations. Existing projects keep their current authority and legacy publisher path until an admin explicitly activates this new binding.

1. Provide a Railway **Project token** scoped to the selected project/environment, either using the password field with explicit storage consent or `RAILWAY_ONBOARDING_PROJECT_TOKEN` on the Lab server. The per-project credential is encrypted with AES-256-GCM using a key derived from SESSION_SECRET. Public/admin/runner responses never return plaintext, ciphertext or authentication headers; no credential is passed to Codex/Mac. Changing SESSION_SECRET requires re-entering credentials. The feature issues only fixed read-only GraphQL queries against `https://backboard.railway.com/graphql/v2` with the Project-Access-Token header. It reads no variables, logs or secrets. A project token may have broader provider capabilities; Lab does not use mutation access. Rotate/revoke tokens in Railway when required.
2. Paste the exact service URL containing project/service/environment UUIDs and an HTTPS `*.up.railway.app` health URL. Custom domains are not enabled in this version. Source repository, branch triggers, service/environment ownership, generated domain, configured healthcheckPath and latest SUCCESS deployment must match. Configured build/start presence and root directory are recorded; commands are not executed or exposed. Automatic publishing is blocked when a pre-deploy command exists, pending separate review.
3. Choose observe (audit only, preserve all settings), requests (enable coding, no release), publish (release after acceptance), or auto (existing single-approval automatic completion after all gates). High-risk approval, exact scope, CI and FIFO remain authoritative. These options never alter another project or grant authority to historical requests.
4. Save explicit consent. Verify manually then apply (which verifies again), or opt into bounded automatic observation/application. A durable job observes at most 30 times and 20 minutes, with 30-second spacing; no model or deployment retries. Cancellation changes no project authority and wins over in-flight remote reads. Credential/project/library revisions invalidate stale consent. A restarted server resumes only waiting automatic jobs.

Readiness independently requires current target HEAD writer-check/browser-check from GitHub Actions, a Railway-bot commit status bound to the exact project/service/environment/deployment ID, a Railway-bot GitHub deployment for that SHA/environment, successful latest deployment status and a no-redirect HTTP 2xx health request. Main, deployment status and Railway configuration are re-read after remote I/O. Health checks attest availability, not business behavior. Library must match verified HEAD before activation.

Operational activation is atomic and blocked by unfinished requests/live or expired claims. It requires a connected Mac; publication additionally requires fresh runner telemetry with `railway-onboarding-v1` and local publisher opt-in. Installed Mac runtime needs an idle update; cloud publisher setup is not implicitly granted. Observe mode stores only audit proof, without changing project settings. Legacy enable/target-edit controls cannot bypass validation for newly bound projects; disabling remains available.

New bound releases require an upgraded publisher claim, a server-side configuration guard before publication, and independent server verification of Railway/GitHub/health before deployed is recorded. Existing unbound releases keep their old protocol. Recovery of newly bound deployments also rechecks the provider binding. Local credentials/config and active worktrees are not rewritten by deploying Lab.

References: [Railway Public API](https://docs.railway.com/integrations/api), [service configuration](https://docs.railway.com/integrations/api/manage-services), [healthchecks](https://docs.railway.com/deployments/healthchecks), and the [official CLI GraphQL schema](https://github.com/railwayapp/cli/blob/master/src/gql/schema.json). The query intentionally follows the actual schema: ServiceSource has repo/image; branch verification uses service repoTriggers.
